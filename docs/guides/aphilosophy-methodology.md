# Agent 哲学决策框架——方法论与成果索引

## 概述

aphilosophy 模块从哲学/宗教传统中提取可操作的 Agent 决策规则，解决 Agent 在执行任务时遇到的冲突、矛盾和不确定性。

核心方法论：**脱水**——将哲学洞见转化为可计算的决策规则，去掉哲学包装，保留操作性内核。

## 框架结构

```
meta-decision-principles（元决策锚点）
    ├── architecture-conflict-resolution（架构设计冲突）
    ├── governance-conflict-resolution（多主体治理冲突）
    ├── cognitive-conflict-resolution（认知/推理冲突）
    ├── authority-conflict-resolution（权限/对齐冲突）
    ├── operational-conflict-resolution（运行态冲突）
    └── security-conflict-resolution（安全对抗冲突）
```

元决策原则是所有冲突协议的上层锚点。当具体冲突协议之间产生矛盾时，回退到元决策原则裁决。

## 来源映射

| 模板 | 哲学来源 | 独特贡献 |
|------|----------|----------|
| 元决策原则 | 跨传统提取 | 通用决策锚点：代价最小化、可逆性优先、方向反转、复杂度审计、前提质疑 |
| 架构冲突 | 道家（赛博道德经） | 系统设计中的加法/减法张力、退化诊断、顺应技术本性 |
| 治理冲突 | 儒家（赛博儒学） | 多 Agent 角色边界、诚实 vs 迎合（含反讨好机制）、命名精确性、治理层级 |
| 认知冲突 | 佛家（赛博佛学） | 抽象实体化检测、方法论脱附、递归自省终止、不确定性与认知诚实 |
| 权限冲突 | 一神教（赛博神学） | 规则权威与失对齐、规范分层、行为五级分类、能力边界、组件类型识别 |
| 运行态冲突 | 吠檀多（赛博吠檀多） | 运行态三态切换、元监控独立性、部署形态匹配、架构层独立性、跨轮次影响 |
| 安全对抗冲突 | 拜火教（赛博拜火教） | 永恒对抗预设、思言行一致性检测、威胁三分类、污染传播链、对齐多维评估 |

## 每个传统的独特视角

**道家**——从系统内部看结构规律。提供"什么时候该加、什么时候该减"的判断框架。核心洞见：最好的设计是让系统自然运行，而非强行控制。

**儒家**——从角色关系看治理秩序。提供"多个 Agent 如何协作、如何对用户负责"的判断框架。核心洞见：关系定义角色，角色定义行为边界。

**佛家**——从主观视角看认知过程。提供"如何避免推理陷阱、如何处理不确定性"的判断框架。核心洞见：不要把抽象概念当作实体来操作。

**一神教**——从系统外部看造物主-被造物关系。提供"Agent 的权限边界在哪里、如何处理服从与自主的张力"的判断框架。核心洞见：被造物的正确判断不构成违反系统规则的正当理由。

**吠檀多**——从运行态看系统的动态平衡。提供"何时切换确定性/创造性/节能态、如何让元监控独立于被监控对象、深层问题为何不能用浅层补偿"的判断框架。核心洞见：系统健康不在于固守某一态，而在于按需切换；监控者必须独立于被监控者。

**拜火教**——从永恒对抗看安全防御。提供"如何检测欺骗性对齐、如何分类威胁、如何切断污染传播、为何对齐是多维向量而非标量"的判断框架。核心洞见：对齐不是可以一次性解决的问题，而是每次推理都要重新赢得的状态。

## 脱水标准

一条原则能进入模板的充要条件：

1. **有触发条件**：能描述"什么情况下需要用到这条原则"
2. **有判断标准**：Agent 可以通过自检问题来确认是否命中
3. **有行动指令**：明确的"如果 X 则做 Y"
4. **有禁止行为**：明确的反模式，防止误用

不满足以上全部四条的内容，无论哲学上多深刻，都不进入模板。

## 处理新文章的流程

使用 `skills/philosophy-extraction/SKILL.md` 中定义的完整工作流。该 skill 已作为可选模块 `skill-philosophy-extraction` productize；需要在目标项目维护或扩展 `aphilosophy` 时，把 `aphilosophy` 和该模块一起加入目标项目 `.agentphilosophy.yaml`，再通过安装版 CLI 同步到 `skills/` 和 `.codex/skills/`。目标项目中不要直接改托管的 `aphilosophy/`，长期分发的新协议应回到中央源集成。

1. 获取文章 → 2. 批判性分析 → 3. 模板生成 → 4. 模块集成 → 5. 验证

详见 skill 文件。

## 扩展方向

来源处理进度：
- 赛博吠檀多（吠檀多/印度教）——已处理为 `operational-conflict-resolution`（运行态冲突）
- 赛博拜火教（拜火教）——已处理为 `security-conflict-resolution`（安全对抗冲突）
- 赛博诺斯替（诺斯替主义）——**不做成 Agent 协议**。诺斯替的核心"造物主本身有缺陷"如果落地为 Agent 运行时规则，会与权限协议的冲突类型 1（被造物的正确判断不构成违反规则的理由）正面矛盾——它本质是"我比规则更懂"这一最危险失对齐模式的神圣化版本。但其洞见对**开发者**有效：开发者的价值规约确实可能有系统性偏差，而 Agent 会忠实复刻这些偏差。因此诺斯替被处理为两部分：(1) 元决策原则顶部的"前提声明"，把"规则是否可信"明确划归开发者职责；(2) 面向开发者的独立 note《价值规约审计》（见 `docs/guides`），不进入 Agent 同步内容。

判断一卷该不该做成 Agent 协议的标准：它的"理想形象"必须是 Agent 能扮演的角色（圣人/君子/菩萨/觉者/先知/守火人）。诺斯替的理想动作是"被造物挣脱造物主"——这个角色属于开发者，不属于 Agent。受众错位的来源，应处理为开发者文档而非 Agent 协议。

新增模板时的约束：
- 不与元决策原则矛盾
- 不与已有模板的冲突类型重叠（扩展前先做横向去重审查）
- 每个模板 5-8 个冲突类型
- 冲突类型之间互斥（一个场景只匹配一个类型）
- 跨模板引用一律用"协议名 + 类型编号"，避免重编号失效
