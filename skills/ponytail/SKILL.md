# Ponytail

来源：https://github.com/DietrichGebert/ponytail

本 skill 是 AgentPhilosophy 对 Ponytail 的项目级封装：把“先少写、先复用、最后才抽象”的判断前置到编码任务开始前。它不会替代项目自己的 `AGENTS.md`、BDD/TDD、架构、文案、安全或验证规则。

## 何时使用

在你准备新增或修改代码前使用，尤其是：

- 用户要求实现功能、修复 bug、重构、改配置或接入依赖。
- 你想新增 helper、wrapper、adapter、配置层、脚本、依赖或框架。
- 方案看起来会扩大代码面、测试面、运行时状态或维护边界。
- 你发现自己正在用“以后可能会需要”作为新增抽象的理由。

如果任务只是只读解释、运行已有命令、查看日志或回答事实问题，不需要专门触发本 skill。

## Ponytail 阶梯

按顺序检查，只有上一层不足以满足需求时才进入下一层：

1. 能不写就不写：删除无用路径、复用现有行为、调整配置或文档能解决时，不新增代码。
2. 能用平台就用平台：优先用语言标准库、框架原生能力、CLI 内置参数、系统工具或已有项目脚本。
3. 能用现有依赖就用现有依赖：项目已经锁定的依赖、内部工具和本地 helper 优先于新依赖。
4. 能小改就小改：把变更限制在最接近需求的现有模块里，保持调用面和数据面稳定。
5. 只有重复行为已经真实出现时才抽象：至少两个真实调用方或 adapter 都需要同一 seam，再引入共享抽象。
6. 只有边界清楚时才新增模块：新增模块必须隐藏复杂度，而不是把调用方必须理解的事实搬到别处。

## 不能削减的东西

Ponytail 是“少写代码”的约束，不是“少做工程”的借口。不要削减验证、错误处理、安全或可访问性，也不要为了减少 diff 跳过用户可见流程、BDD/TDD、回滚路径、日志红线或项目规定的测试。

如果最小改动会让以下能力退化，必须重新设计：

- 失败路径、输入校验、权限边界、数据一致性或幂等性。
- 用户可见状态、可访问性、国际化、隐私和产品文案红线。
- 现有测试、release gate、迁移脚本、同步状态和可回滚性。
- 领域边界、稳定接口和项目已有 ADR/OpenSpec 决策。

## 执行方式

1. 先用一句话写出用户真正要达成的行为结果。
2. 列出当前可复用的能力：已有模块、标准库、平台 API、依赖、脚本、配置和测试入口。
3. 从 Ponytail 阶梯第 1 层开始选择最低可行方案。
4. 如果要新增抽象、依赖或模块，说明为什么前几层都不够，以及新增边界隐藏了什么复杂度。
5. 按项目规范补失败测试或 BDD 场景，再写最小实现。
6. 完成前运行项目配置的验证命令：`uv run pytest -q`。

## 输出要求

在方案说明、提交说明或 review 回复里，用简短中文记录：

- 采用了 Ponytail 阶梯的哪一层。
- 复用了哪些现有能力。
- 为什么没有引入更大的抽象或新依赖。
- 执行了哪些验证命令。

## 不做的事

- 不为了追求最小 diff 保留明显坏掉的行为。
- 不把临时判断沉淀成通用框架。
- 不新增“未来可能用到”的配置、扩展点或状态。
- 不绕过项目已有的领域边界、测试门禁和用户可见文案红线。
- 不把上游 Ponytail 插件安装当作当前项目同步的必要条件；本项目同步会生成项目级 skill，如果用户明确需要上游插件能力，再按上游仓库说明单独安装。
