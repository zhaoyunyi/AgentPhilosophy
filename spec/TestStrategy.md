# 测试策略

## 编写测试注意事项

1. **测试行为，不测试实现。** 通过公开接口验证用户可观察的结果、业务状态和副作用，例如“重复下单不会重复扣款”。不要用某个内部方法的调用次数、私有状态或调用顺序代替业务结果。业务合同未变的重构应继续通过原有测试；若仅调整内部结构就导致大量测试失败，先检查断言是否耦合了实现。
2. **先写 BDD 验收场景，再写代码。** 从需求和业务规则推导场景，覆盖成功路径和关键失败路径；测试描述统一以 `user` 开头，用用户和产品经理能理解的语言写明 Given / When / Then。先确认场景能够暴露尚未实现或错误的行为，再实现并验证通过。AI 生成测试同样遵守这个顺序，不能在代码写完后照着实现补断言、自证正确。

示例：

```gherkin
Scenario: user 重复下单不会重复扣款
  Given 用户已成功支付一笔订单，账户已扣除一次订单金额
  When 用户使用同一下单标识再次提交该订单
  Then 用户获得同一笔订单，账户余额不再减少，扣款记录仍只有一笔

Scenario: user 支付被拒绝后不会被扣款
  Given 用户有一笔待支付订单，支付渠道将拒绝本次支付
  When 用户尝试支付该订单
  Then 用户看到支付失败，订单仍未支付，账户余额不变且没有扣款记录
```

## 分层

- 单元测试：覆盖纯逻辑、路径安全、hash/state 和边界条件。
- BDD 测试：覆盖用户可观察流程。
- e2e 测试：覆盖 CLI 或真实运行入口的完整链路。

## 默认命令

`uv run pytest -q`
